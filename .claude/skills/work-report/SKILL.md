# گزارش کار — قالبِ ثابت (دستور حمید، ۲۴ اوت)

حمید: «تا گفتم گزارش کار را بده، نتایج را **با جزئیات و خلاصه و دقیق**
بهم بگو. چیز دیگری هم نیاز بود اضافه می‌کنم.»

پس این گزارش هر بار یک شکل دارد. نه کوتاه‌تر می‌شود چون خبرِ بدی نبوده،
نه بلندتر چون خبرِ خوبی بوده.

## گام ۰ — دفتر باید تازه باشد (وگرنه گزارش دروغ می‌گوید)

عیب واقعیِ ۲۴ اوت: `git fetch` روی این ریپو timeout خورد، دفترِ محلی یک
روز عقب ماند، و اعداد «دیشب تا الان» صفر معامله نشان دادند در حالی که
چرخه سالم کار می‌کرد. **قبل از هر عددی:**

```bash
timeout 1500 git fetch --depth=1 origin main
git log -1 --format=%cI FETCH_HEAD        # باید نزدیک الان باشد
timeout 900 git show FETCH_HEAD:brain/paper/closed.jsonl > /tmp/closed.jsonl
```

اگر تاریخ FETCH_HEAD کهنه بود، **اول همین را بگو** و بعد عدد بده. سکوتِ
دفتر ≠ سکوتِ بازار؛ فرقشان را با وضعیت `hamid-cycle` در Actions روشن کن.

## گام ۱ — موتور را اجرا کن، متن ننویس

```bash
cd claude-liam-signal/python
python3 -m hamid.work_report --hours 20      # یا بدون --hours: از ۰۰:۰۰ UTC
python3 -m hamid.work_report --json          # نسخهٔ کامل
```

هر عددِ گزارش باید از همین خروجی بیاید. عددی که با دست حساب شده و راه
بازتولید ندارد، در گزارش نمی‌آید (قانون گزارش‌دهی، CLAUDE.md).

## گام ۲ — ساختار پاسخ (همیشه همین ترتیب)

1. **خلاصهٔ سه‌خطی** — سرخط: سیگنالِ ارسال‌شده چند به چند، انتظار چقدر،
   خالص از کارمزد چقدر. اگر دفتر تازه نبود، همین‌جا گفته شود.
2. **جدول دفترها** — هر دفتر جدا (سیگنال ارسالی، اسکلپ، شوک، تمرین، v2)
   با n / برد٪ / انتظار / خالص. دفترهای آزمایشی و وتوشده **زیر خط جدا**
   با برچسب «ادعای عملکرد نیست».
3. **تایم‌فریم** — «موفقیت در کدام تایم بیشتر بوده؟» همیشه با **پوشش**:
   روی چند درصدِ نمونه `tf` وجود داشته. تایمِ زیر ۸ نمونه «بهترین»
   اعلام نمی‌شود.
4. **استاپ و تارگت** — شمارش استاپ/تارگت/تریل، MFE/MAE، مدت نگهداری، و
   عددِ کلیدی: **چند استاپ قبلاً در سود بوده‌اند** و تا کجا رفته بودند.
5. **اثر تجربه** — سه پنجره (همین گزارش / ۷ روز / کل دفتر)، هر کدام با
   بازهٔ اطمینان و حکم صریح. بازه‌ای که صفر را در بر بگیرد **حتماً**
   «از نویز جدا نیست» خوانده می‌شود.
6. **اثر مهارت/انجین‌ها** — کارنامهٔ `brain/rewards.json` با یادآوری
   این‌که جایزه ردپای تأیید است نه اثرِ علّی.
7. **چه چیزی از این گزارش تغییر می‌کند** — یک تغییرِ کنترل‌شده، و
   این‌که چرخهٔ بعد چطور نمره‌اش می‌دهد. اگر هیچ‌چیز CI بالای صفر
   نداشت، صریح بگو «تغییری موجه نیست».

## گام ۲.۵ — تمرکز انجین‌ها + بندیت (دستور حمید، ۳۱ اوت)

حمید: «هر بار که گزارش می‌گیری روی نقاط قوت هر انجین تمرکز کن و کارهای
اساسی و منابع مهم را در اختیارشان بگذار... و هر بار که نتیجه را می‌بینی
با اطلاعات جدید تستشون کن.»

```bash
python3 -m hamid.bandit --focus     # یا --write برای signals/engine-focus.json
```

بخش «انجین‌ها» در هر گزارش باید از همین خروجی بیاید: نقطهٔ قوتِ
اندازه‌گیری‌شدهٔ هر انجین (نرخ tp/stop و امتیاز بر معامله)، منابعِ
قفسه‌اش، و وضعیت بازوهای آزمایشِ بندیت (n، CI، حکم، سهم امروز). سه قید:
جایزه ردپای تأیید است نه اثر علّی؛ انجینِ زیر ۴۰ نمونه برچسبِ قوی/ضعیف
نمی‌گیرد؛ و بندیت فقط بودجهٔ آزمایش پیپر را تقسیم می‌کند — دروازه نیست.

## گام ۳ — سه قیدی که هرگز شکسته نمی‌شوند

- **یک روزِ خوب یا بد، یادگیری را نه اثبات می‌کند نه رد.** نمونهٔ ۲۳
  اوت: همان داده روی دفتر چندروزه +۰.۴۴۳R معنادار داد و روی نمونهٔ
  یک‌روزه −۰.۰۷۰R با CI شاملِ صفر. هر دو درست بودند
  (`.claude/rules/03-learning-memory-governance.md`).
- **پیپر سقف خوش‌بینانه است** — فیل کامل، بی‌لغزش. عددِ سیگنالِ
  واقعاً ارسال‌شده جدا گزارش می‌شود.
- **شبیه‌ساز ادعای عملکرد نیست.** اگر عددی از شبیه‌ساز آمد، صریح گفته
  می‌شود؛ ادعای عملکرد فقط از `python/backtest.py` روی کندل واقعی.

## گام ۴ — قانون سه‌بار خواندن

آخرِ کار، پیام حمید را دوباره بخوان و تک‌تک خواسته‌هایش را با گزارش
تطبیق بده. اگر چیزی را نتوانستی بدهی (مثل تایم‌فریمی که دفترش پوشش
ندارد)، **صریح بگو چرا** — حذفِ بی‌صدا ممنوع است.
